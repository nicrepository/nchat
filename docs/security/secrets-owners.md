| nchat-file-encryption         | nchat, nchat-dev | Dev B / Infra | manual on incident or key compromise | RF-33/RNF-17 attachment envelope-encryption key ring (`FILE_ENCRYPTION_MASTER_KEY`, `FILE_ENCRYPTION_MASTER_KEY_ID`, `FILE_ENCRYPTION_PREVIOUS_KEYS`). Scoped to file-service alone — deliberately not in `nchat-secrets`, which every service mounts with `envFrom`. Rotation is not a cadence job: retiring a key before every attachment it wrapped has been rewrapped makes those files permanently unreadable. Procedure: `docs/runbooks/file-service-envelope-encryption.md` |

## Losing the attachment key ring

`nchat-file-encryption` is the only copy of the keys that protect attachment
content. SeaweedFS holds ciphertext, PostgreSQL holds the wrapped data keys, and
neither holds a KEK — which is the point, and also means a lost KEK is
unrecoverable data loss for every attachment wrapped under it. Treat it like a
root credential: escrow it wherever the organisation escrows those, and never
remove a key id from `FILE_ENCRYPTION_PREVIOUS_KEYS` until the rewrap for that id
reports zero remaining rows.
